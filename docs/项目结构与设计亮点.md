## 一、顶层目录树

```text

│   ├── config/                 # config.toml + dev/test/prod profile（三层覆盖）

│   ├── uploads/ downloads/     # 上传 / 导出落盘目录
│   └── src/
│       ├── main.rs             # 入口：cailu::run()
│       ├── lib.rs             # run()：App 装配与固定启动链
│       ├── bootstrap.rs        # 启动引导：管理员账号、字典/配置预热、任务装载
│       ├── shared/             # 横切：constants / error_code
│       ├── middleware/         # 横切：操作日志中间件
│       ├── task/               # 横切：定时任务调度器
│       ├── utils/              # 横切：纯工具函数（require_uuid / normalize_page / db_error ...）
│       ├── system/             # 业务容器一（框架底座）：auth/user/role/menu/dept
│       ├── support/            # 业务容器二（框架底座）：health/dict/config/file/log/job/online
│       └── business/           # 【二开容器】新业务模块放这里（当前为空，从 V0020 起）
├── frontend/                   # 前端：Vue 包 @cailu/web（Vite + TDesign + Pinia）
│   ├── vite.config.ts          # 代理 /api、/health → 127.0.0.1:8023
│   ├── deploy/nginx.conf       # 生产 nginx 站点配置
│   └── src/
│       ├── api/                # 接口封装：system/*、support/*、business/*（二开）
│       ├── router/             # 路由表 + 权限守卫
│       ├── stores/             # Pinia：user（会话/权限/菜单）、dict（字典缓存）、setting（主题）
│       ├── layouts/            # BasicLayout（侧边栏 / 顶栏 / 内容区）
│       ├── views/              # 页面：system/*、support/*、business/*（二开）、login/dashboard/user/result
│       ├── components/         # DeptTreeSelect / DictTag / DictSelect / FileUploader
│       ├── directives/         # v-privilege 权限指令
│       ├── utils/ types/       # 格式化、菜单路径、全局错误兜底；与后端 DTO 对齐的 TS 类型
│       └── style/              # index.less + theme.less（明暗双主题、品牌渐变变量）
├── docs/                       # 二开文档集（见 README.md）
├── docker/                     # 部署编排：dev 依赖 compose（PG+Redis）、prod 完整编排、Dockerfile
└── scripts/                    # dev / check / build / deploy / init-db 一键脚本
```

## 二、后端分层职责

`lib.rs` 顶部的启动链是理解整个后端的钥匙：

```rust
App::new()?                          // 读 config.toml + profile 覆盖，初始化日志
    .parse_cli()                     // 解析 gen-config / print-config / profile=xxx
    .get("/health", support::health::health)   // 手动注册存活探针（豁免 /api 前缀）
    .on_startup(bootstrap::bootstrap) // 全局资源就绪后：管理员账号、字典/配置预热、任务装载
    .plugin(support::log::plugin::LogPlugin::new())  // 日志总线插件
    .plugin(task::scheduler())        // 定时任务调度器插件
    .layer_from_fn(middleware::operation_log::layer) // 操作日志中间件（覆盖整站）
    .scan()                          // 自动收集 #[alun::*] 宏声明的路由
    .start()                         // 初始化 DB/缓存、启动插件、监听 [server].listen
    .await
```

**业务容器 vs 横切层**：
- `system/` 与 `support/` 是**框架内置底座**；**新业务代码一律放 `business/`**，与底座平级隔离、互不侵入。
- `middleware / task / utils / shared / bootstrap` 是**横切关注点**，放在业务容器之外，业务模块不依赖框架装配细节。

**业务子模块统一四件套**（以 `system/user/` 为例）：

```text
system/user/
├── mod.rs      # 模块文档 + 子模块声明（pub mod dto; mod handler; mod model;）
├── handler.rs  # 路由处理器：参数校验、业务编排、响应构造（路由方法在前，公共辅助在后）
├── dto.rs      # 请求/响应 DTO（*Req / *Res），与前端契约严格对齐
└── model.rs    # 强类型模型（*Model）+ 数据访问 + 领域行为
```

> **不设 service 层**：业务编排写在 `handler.rs`，数据访问与领域行为写在 `model.rs`。需要自写 SQL（动态 SQL / 复合条件 / `sql!` 宏）或封装领域逻辑时放 `model.rs`；仅调用框架快捷方法（`find_or_none` / `find_by` / `count_by` / `of(...).set(...).update(...)`）时在 `handler.rs` 直接调用。

## 三、数据库：17 张表

| # | 表名 | 说明 | 软删 | 所属域 |
|---|------|------|------|--------|
| 1 | `sys_user` | 用户 | 是 | system |
| 2 | `sys_role` | 角色 | 是 | system |
| 3 | `sys_user_role` | 用户-角色关联（硬删） | 否 | system |
| 4 | `sys_menu` | 菜单与权限点 | 是 | system |
| 5 | `sys_role_menu` | 角色-菜单关联（硬删） | 否 | system |
| 6 | `sys_dept` | 部门机构 | 是 | system |

| 8 | `sys_dict_item` | 字典项 | 是 | support |
| 9 | `sys_config` | 系统参数 | 是 | support |
| 10 | `sys_file` | 文件元数据 | 是 | support |
| 11 | `operation_logs` | 操作日志（追加写） | 否 | support |
| 12 | `sys_job` | 定时任务定义 | 是 | support |
| 13 | `sys_job_log` | 任务执行日志（追加写） | 否 | support |
| 14 | `audit_logs` | 审计日志（前后快照，追加写） | 否 | support |
| 15 | `auth_logs` | 认证日志（追加写） | 否 | support |
| 16 | `security_logs` | 安全日志（追加写） | 否 | support |
| 17 | `password_change_logs` | 密码变更日志（追加写） | 否 | support |

**通用约定**：
- 主键 `UUID`，应用侧写 `Uuid::now_v7()`（时间有序，避免 B-tree 随机插入）；`created_at / updated_at TIMESTAMPTZ` 由 `TimestampHook` 维护。
- 软删统一 `deleted_at TIMESTAMPTZ`（NULL = 未删除）；软删表的唯一列用**部分唯一索引** `... WHERE deleted_at IS NULL`，删除后可重建同名。
- 状态列 `SMALLINT`（`TypeMapper` 枚举，1 启用 / 0 禁用）；审计列 `create_by / update_by`；布尔列 `BOOLEAN`（`is_` 前缀）。
- 日志类表「只写 + 不提供修改接口」，硬删、无 `updated_at`。

## 四、设计亮点（Alun 框架为什么这么设计）

### 4.1 门面化依赖，一处声明全量能力
`Cargo.toml` 只声明 `alun` 一个框架 crate，数据库 / Web / 缓存 / 配置 / 文件 / 插件等能力全部通过 **feature 选择**，业务代码统一 `use alun::prelude::*` 转发。
> **铁律**：依赖清单中**不出现** `alun-db` / `alun-db-core` / `alun-web` / `alun-config`。杜绝分 crate 版本漂移与「多份实例」问题。
> **对二开**：加能力只改 `features = [...]`，绝不 `cargo add alun-db` 之类。

### 4.2 声明式模型，查询/写入职责分明
- `#[derive(Model)]` 声明实体：表名由结构体名蛇形推导（可 `#[table]` 显式指定）、`id` 即主键、`created_at/updated_at` 自动挂 `TimestampHook`、`Option<DateTime>` 的 `deleted_at` 自动作为软删标记。
- **查询是关联函数、持久化是实例方法**：`SysUserModel::find / query`、`.insert / .update / .delete`、`ChangeSet` 局部更新、`TypeMapper` 枚举映射（`#[int]` / `#[value_map]`）。
- 多条件查询用 `sql!` 宏的 `#if / #and / #or`，**不做字符串拼接**，插值自动参数化（天然防 SQL 注入）。
- 首参统一 `&impl SqlExecutor`：`&Db` 与 `&Transaction` 通用，Model API 在事务内同样可用。

### 4.3 宏声明路由、权限与免鉴权
- `#[alun::get/post/put/patch/delete]` 在处理器上声明路由，`App::scan()` 启动时**自动收集**，无需手工注册。
- `#[alun::permission("system:user:create")]` 声明权限码；`#[alun::no_auth("/path")]` 声明免鉴权白名单。
- 全局前缀由 `[router] prefix` 集中配置，宏内路径不含前缀，避免硬编码散落。

### 4.4 三层配置 + 配置化中间件
- `config.toml` → `config-{profile}.toml` → `ALUN_*` 环境变量；profile 选取 `命令行 > ALUN_PROFILE > ALUN_ENV > 默认 dev`。
- 认证、CORS、限流、安全头、压缩、幂等、nonce 等中间件**全部配置化开关**，开发/生产差异只改配置不改代码。
- 敏感值（JWT 密钥、数据库密码）生产环境强制环境变量注入（`ALUN_MIDDLEWARE_AUTH_JWT_SECRET` 等）。

### 4.5 内置迁移 runner
- **方言感知的语句拆分器**：单文件可写多条 SQL（`;` 分隔自动逐条执行，`$$…$$` 与字符串/注释内分号不误切），索引与 `COMMENT ON` 可与建表语句同文件。
- 文件内容参与**指纹校验**，已应用迁移被改动即报 `MigrationChecksum`；每个迁移包在**一个事务**中执行，失败整体回滚。
- 种子迁移 `S__*.sql` 用 `ON CONFLICT ... WHERE deleted_at IS NULL` 保证幂等；支持 `COMMENT ON TABLE / COLUMN` 写入数据库目录。

### 4.6 固定启动链与插件机制
- 全局单例访问器 `db() / cache() / cfg()`，不用 axum `State` 层层透传。
- 插件（日志总线、调度器）与中间件钩子即插即用，业务代码零装配细节。
- **事务安全**：RAII 闭包事务，返回 `Err` 自动回滚，绝不允许带未提交事务的连接归还连接池。

### 4.7 横切能力开箱即用
- 请求 ID 注入、请求日志、操作日志中间件（脱敏后记录请求/响应体）、IP 归属地、UA 解析均框架内建或 `alun-utils` 提供。
- 缓存抽象本地/Redis 一键切换，业务代码原语不变。
- 框架预留多租户能力（`#[tenant]` / `TenantLayer`），本版本未启用，后续升级无需改业务层。

## 五、部署模型

```text
浏览器 ──HTTPS──▶ nginx（托管 frontend/dist + 反代 /api、/health）
                       ├── location /        → SPA fallback index.html
                       └── location /api /health → proxy_pass 后端 :8023
                            │
                            ▼
                   cailu 后端（Rust + axum，:8023）
                   ├── REST API（/api/system/* /api/support/*）
                   └── uploads / downloads 文件目录
                            │
                            ▼
                   PostgreSQL（17 张表）  +  Redis（缓存 / 令牌黑名单）
```

- **前后端分离**：前端构建产物由 nginx 托管，`index.html` 不缓存、`/assets/` 长缓存；上传接口需放宽 `client_max_body_size`。
- **容器化（推荐）**：`docker/` 提供两套编排——`docker-compose.yml`（开发依赖 PG+Redis，后端/前端仍本机运行）；`docker-compose.prod.yml`（生产完整编排，后端镜像多阶段编译，`scripts/deploy.sh` 自动暂存框架源码进构建上下文）。

## 六、默认配置速查

| 配置段 | 字段 | 默认值 | 说明 |
|--------|------|--------|------|
| `[server]` | `listen` | `8023` | 后端监听端口 |
| `[database]` | `name` | `cailu` | 数据库名 |
| `[database]` | `auto_migrate` | `true` | 启动自动迁移 |
| `[middleware.auth]` | `enabled` | 各环境均开 | 认证中间件 |
| `[middleware.auth]` | `jwt_secret` | profile 内固定值 | **生产必须用 `ALUN_MIDDLEWARE_AUTH_JWT_SECRET` 注入** |
| `[middleware.cors]` | `allow_origins` | 含 `http://localhost:5173` | 前端 dev 端口 |
| `[upload]` | `max_size_mb` | `20` | 上传大小限制 |

**默认账号**：`admin / Admin@123456`（`SUPER_ADMIN`，跳过全部权限校验；生产用 `ALUN_ADMIN_PASSWORD` 注入，首次登录后改密）。

**生产敏感值注入**：
```text
ALUN_DATABASE_PASSWORD=<pg 密码>
ALUN_MIDDLEWARE_AUTH_JWT_SECRET=<jwt 密钥，至少 32 字符>
ALUN_ADMIN_PASSWORD=<初始管理员密码>
ALUN_SERVER_LISTEN=0.0.0.0:8023
```
